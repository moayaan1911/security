Protocol Summary

TSwap is a fork of Uniswap V1: a permissionless automated market maker where each pool holds WETH and one other token. Liquidity providers deposit both sides and receive LP tokens that represent their share of the pool and earn a cut of the 0.3% swap fee. Swappers trade against the pool, where the price is set by the reserves following the constant product formula x * y = k. A factory contract deploys one pool per token and keeps a registry of them.

Roles

  • Liquidity providers: deposit WETH and pool tokens, receive LP tokens, and withdraw their share.
  • Swappers: call swapExactInput, swapExactOutput or sellPoolTokens against a pool.
  • Pool creators: anyone can call PoolFactory::createPool for any token, the factory is permissionless.
  • Admins: there is no owner or admin role in either contract, so there are no privileged functions.

Executive Summary

This was a time-boxed review of TSwap, using static analysis with Slither and Aderyn, a manual review, and an invariant test suite written during the review. The review found 2 High, 2 Medium, 1 Low and 17 Informational findings. The most serious are the wrong fee in getInputAmountBasedOnOutput, which charges exact output swappers about 10x the fair input, and the swap incentive in _swap, which pays out 1e18 of the output token every tenth swap and breaks the pool’s x * y = k invariant. Every High, Medium and Low finding has a working Foundry test as proof of concept, and the X/Y invariant tests written during the review pass. Slither returned no high risk results, while Aderyn reported one High (a reentrancy pattern in the factory) which was triaged down to Informational because no funds are at risk.

Findings

High

[H-1] Wrong fee in TSwapPool::getInputAmountBasedOnOutput, exact output swaps charge the caller about 10x the fair input

Description: getInputAmountBasedOnOutput works out how much input a caller must pay for an exact output amount, but the fee multiplier is 10000 where it should be 1000:

return
    ((inputReserves * outputAmount) * 10000) /
    ((outputReserves - outputAmount) * 997);

The mirror function, getOutputAmountBasedOnInput, uses the correct 997 / 1000 fee pair, which is what makes the mistake obvious:

uint256 inputAmountMinusFee = inputAmount * 997;
uint256 denominator = (inputReserves * 1000) + inputAmountMinusFee;

So the required input comes out roughly 10x too large.

Impact: Every caller of swapExactOutput is overcharged about 10x, and sellPoolTokens routes through the same function. The extra tokens stay in the pool, so the caller loses real funds on every exact output swap while the liquidity providers gain at their expense. It also makes the pool’s own invariant (x * y = k) blow up in the pool’s favour instead of holding.

Proof of Concept: Check the test_SwapExactOutputOvercharges_AUDIT test in the TSwapPool.t.sol file:
Here’s the full code 
    // the HIGH: getInputAmountBasedOnOutput multiplies by 10000 instead of 1000,
    // so an exact output swap charges the caller roughly 10x the fair input
    function test_SwapExactOutputOvercharges_AUDIT() public {
        vm.startPrank(liquidityProvider);
        weth.approve(address(pool), 100e18);
        poolToken.approve(address(pool), 100e18);
        pool.deposit(100e18, 100e18, 100e18, uint64(block.timestamp));
        vm.stopPrank();

        uint256 wethReserves = weth.balanceOf(address(pool));
        uint256 poolTokenReserves = poolToken.balanceOf(address(pool));
        uint256 outputWeth = 0.5e18;

        // the same formula with the fee applied once, which is what the caller should pay
        uint256 fairInput = (poolTokenReserves * outputWeth * 1000) /
            ((wethReserves - outputWeth) * 997);

        // what the pool actually asks for
        uint256 quotedInput = pool.getInputAmountBasedOnOutput(
            outputWeth,
            poolTokenReserves,
            wethReserves
        );

        console.log("charged input:", quotedInput);
        console.log("fair input:", fairInput);

        assertGt(quotedInput, fairInput * 9);

        // and it is what the caller really pays
        vm.startPrank(user);
        poolToken.approve(address(pool), type(uint256).max);
        uint256 balanceBefore = poolToken.balanceOf(user);
        pool.swapExactOutput(
            poolToken,
            weth,
            outputWeth,
            uint64(block.timestamp)
        );
        uint256 paid = balanceBefore - poolToken.balanceOf(user);
        vm.stopPrank();

        console.log("actually paid:", paid);
        assertEq(paid, quotedInput);
        assertGt(paid, fairInput * 9);
    }

You can run it via

forge test --mt test_SwapExactOutputOvercharges_AUDIT -vv

and you will see something like this:

Logs:
  charged input: 5040246367242430810
  fair input: 504024636724243081
  actually paid: 5040246367242430810

The caller pays 5.04e18 pool tokens for 0.5e18 WETH, where the fair price is 0.504e18. A clean 10x, and the pool really takes that much, it is not just the quote function.

Recommended Mitigation: 1. Use 1000 in the numerator, so the fee is applied once like every other AMM:

-        return
-            ((inputReserves * outputAmount) * 10000) /
-            ((outputReserves - outputAmount) * 997);
+        return
+            ((inputReserves * outputAmount) * 1000) /
+            ((outputReserves - outputAmount) * 997);
  1. Replace the 997, 1000 and 10000 literals with named constants in both pricing functions, so the fee is defined once and the two functions cannot drift apart again:
+    uint256 private constant FEE_MULTIPLIER = 997;
+    uint256 private constant FEE_BASE = 1000;

The names matter: 997/1000 is the fee factor, and the exact output formula uses its inverse (FEE_BASE / FEE_MULTIPLIER), so naming them after the fee factor avoids repeating this mistake.

[H-2] Swap incentive in TSwapPool::_swap pays out 1e18 of the output token every 10th swap, breaking the x * y = k invariant

Description: Every tenth swap, _swap sends the caller an extra 1e18 of the output token, straight out of the pool’s reserves:

swap_count++;
if (swap_count >= SWAP_COUNT_MAX) {
    swap_count = 0;
    outputToken.safeTransfer(msg.sender, 1_000_000_000_000_000_000);
}

The pool pays that token out without receiving any input for it, so it is a direct transfer from the liquidity providers to the caller.

Impact: The pool’s x * y = k falls every tenth swap instead of holding or growing, which means liquidity providers lose value on a fixed schedule. It is also farmable, since the bonus is a flat 1e18 regardless of swap size, so anyone can make nine dust swaps and take 1e18 on the tenth. And because the transfer happens before the swap is settled, a pool holding less than 1e18 of the output token cannot complete its tenth swap at all, it reverts. In the PoC the bonus is 1.0978e18 WETH received against an expected 0.0978e18, and k drops from 1.0000269e40 to 9.899298e39.

Proof of Concept: Check the test_SwapIncentiveBreaksInvariant_AUDIT test in the TSwapPool.t.sol file:
Here’s the full code 
    // the H-2: every 10th swap pays the caller 1e18 of the output token for free, which drops
    // the pool's x * y = k instead of holding it
    function test_SwapIncentiveBreaksInvariant_AUDIT() public {
        vm.startPrank(liquidityProvider);
        weth.approve(address(pool), 100e18);
        poolToken.approve(address(pool), 100e18);
        pool.deposit(100e18, 100e18, 100e18, uint64(block.timestamp));
        vm.stopPrank();

        vm.startPrank(user);
        poolToken.approve(address(pool), type(uint256).max);

        // nine normal swaps, the tenth is the one that pays the bonus
        for (uint256 i = 0; i < 9; i++) {
            pool.swapExactInput(
                poolToken,
                0.1e18,
                weth,
                0,
                uint64(block.timestamp)
            );
        }

        uint256 wethReserves = weth.balanceOf(address(pool));
        uint256 poolTokenReserves = poolToken.balanceOf(address(pool));
        uint256 kBefore = wethReserves * poolTokenReserves;

        // what the pool itself says this swap should pay out
        uint256 expectedOut = pool.getOutputAmountBasedOnInput(
            0.1e18,
            poolTokenReserves,
            wethReserves
        );

        uint256 wethBefore = weth.balanceOf(user);
        pool.swapExactInput(poolToken, 0.1e18, weth, 0, uint64(block.timestamp));
        uint256 received = weth.balanceOf(user) - wethBefore;
        vm.stopPrank();

        uint256 kAfter = weth.balanceOf(address(pool)) *
            poolToken.balanceOf(address(pool));

        console.log("expected out:", expectedOut);
        console.log("actually received:", received);
        console.log("k before:", kBefore);
        console.log("k after:", kAfter);

        // the caller got 1e18 free on top of the swap
        assertEq(received, expectedOut + 1e18);

        // and the pool's product dropped instead of holding
        assertLt(kAfter, kBefore);
    }

You can run it via

forge test --mt test_SwapIncentiveBreaksInvariant_AUDIT -vv

and you will see something like this:

Logs:
  expected out: 97835298857383282
  actually received: 1097835298857383282
  k before: 10000268662499607603075500000000000000000
  k after: 9899298366356141334213000000000000000000

The pool paid out 1e18 it never received, and the product dropped with it.

Recommended Mitigation: 1. Remove the bonus from the swap path entirely. A pool’s reserves should only ever move by the swap maths.

-    uint256 private swap_count = 0;
-    uint256 private constant SWAP_COUNT_MAX = 10;

...
-        swap_count++;
-        if (swap_count >= SWAP_COUNT_MAX) {
-            swap_count = 0;
-            outputToken.safeTransfer(msg.sender, 1_000_000_000_000_000_000);
-        }

Removing the bonus leaves swap_count and SWAP_COUNT_MAX dead, so delete both declarations for clarity. No compiler warning is involved, solc does not warn about unused state variables.

  1. If the incentive is a product requirement, fund it from a separate rewards contract or an owner funded balance, so paying it never touches LP reserves, and make it proportional to the swap size so it cannot be farmed with dust swaps.

  2. The PoC has to change with the fix. It asserts received == expectedOut + 1e18, which only holds while the bonus is paid, so after removing the bonus it should assert received == expectedOut and that k no longer falls.

Medium

[M-1] No maximum input check in TSwapPool::swapExactOutput, a caller can be charged an input far above the fair price

Description: swapExactInput takes a minOutputAmount so the caller can bound their slippage, but swapExactOutput has no equivalent. It works out the input itself from getInputAmountBasedOnOutput and then swaps straight away, so the caller has no parameter to say “I will not pay more than X”:

inputAmount = getInputAmountBasedOnOutput(
    outputAmount,
    inputReserves,
    outputReserves
);

_swap(inputToken, inputAmount, outputToken, outputAmount);

Impact: A caller who submits an exact output swap can be sandwiched, or simply have their transaction land after the price has moved, and the swap still goes through at the worse price. Nothing reverts and there is no way to protect themselves. In the PoC the same 1e18 WETH output costs 10.13 pool tokens at first and 22.88 pool tokens after one big swap, a 2.26x overpay that the caller cannot stop.

Proof of Concept: Check the test_SwapExactOutputNoMaxInput_AUDIT test in the TSwapPool.t.sol file:
Here’s the full code 
    // the M-1: swapExactOutput has no max input parameter, so a caller can be charged a much
    // worse price and has nothing to protect them (swapExactInput has minOutputAmount)
    function test_SwapExactOutputNoMaxInput_AUDIT() public {
        vm.startPrank(liquidityProvider);
        weth.approve(address(pool), 100e18);
        poolToken.approve(address(pool), 100e18);
        pool.deposit(100e18, 100e18, 100e18, uint64(block.timestamp));
        vm.stopPrank();

        uint256 outputWeth = 1e18;

        // what the caller would pay at the current price
        uint256 inputBefore = pool.getInputAmountBasedOnOutput(
            outputWeth,
            poolToken.balanceOf(address(pool)),
            weth.balanceOf(address(pool))
        );

        // someone swaps first and makes WETH scarcer, moving the price against the caller
        poolToken.mint(user, 100e18);
        vm.startPrank(user);
        poolToken.approve(address(pool), type(uint256).max);
        pool.swapExactInput(poolToken, 50e18, weth, 0, uint64(block.timestamp));
        vm.stopPrank();

        uint256 inputAfter = pool.getInputAmountBasedOnOutput(
            outputWeth,
            poolToken.balanceOf(address(pool)),
            weth.balanceOf(address(pool))
        );

        console.log("input before the price move:", inputBefore);
        console.log("input after the price move:", inputAfter);
        assertGt(inputAfter, inputBefore);

        // the swap still goes through at the worse price, there is no max input to set
        poolToken.mint(user, inputAfter);
        vm.startPrank(user);
        uint256 balanceBefore = poolToken.balanceOf(user);
        pool.swapExactOutput(
            poolToken,
            weth,
            outputWeth,
            uint64(block.timestamp)
        );
        uint256 paid = balanceBefore - poolToken.balanceOf(user);
        vm.stopPrank();

        console.log("paid at the worse price:", paid);
        assertEq(paid, inputAfter);
    }

You can run it via

  input before the price move: 10131404313951956880
  input after the price move: 22888113791382523076
  paid at the worse price: 22888113791382523076

The price moved against the caller and the exact output swap executed anyway, at more than double the input.

Recommended Mitigation: 1. Take a maxInputAmount and revert when the pool asks for more, the mirror of minOutputAmount in swapExactInput:

+    error TSwapPool__InputTooHigh(uint256 inputAmount, uint256 maxInputAmount);
+
     function swapExactOutput(
         IERC20 inputToken,
         IERC20 outputToken,
         uint256 outputAmount,
+        uint256 maxInputAmount,
         uint64 deadline
     )
...
         inputAmount = getInputAmountBasedOnOutput(
             outputAmount,
             inputReserves,
             outputReserves
         );
 
+        if (inputAmount > maxInputAmount) {
+            revert TSwapPool__InputTooHigh(inputAmount, maxInputAmount);
+        }
+
         _swap(inputToken, inputAmount, outputToken, outputAmount);
  1. This adds a parameter to a public function, so sellPoolTokens and any integrator calling swapExactOutput has to be updated in the same change.

[M-2] Wrong amount semantics in TSwapPool::sellPoolTokens, the amount to sell is used as the exact WETH output

Description: sellPoolTokens is documented as “sell this many pool tokens for WETH”, but it forwards the amount to swapExactOutput as the output:

function sellPoolTokens(uint256 poolTokenAmount) external returns (uint256 wethAmount) {
    return
        swapExactOutput(
            i_poolToken,
            i_wethToken,
            poolTokenAmount,
            uint64(block.timestamp)
        );
}

So the caller receives exactly poolTokenAmount in WETH, and pays whatever number of pool tokens the pool decides it needs for that. The value it returns as wethAmount is also wrong: swapExactOutput returns its computed input, so wethAmount is really the pool tokens that were spent.

Impact: The caller gets a completely different trade than they asked for. In the PoC a seller asking to sell 5e18 pool tokens is charged 52.78e18 pool tokens to receive exactly 5e18 WETH, and a seller holding 10e18 pool tokens, twice what they intend to sell, still reverts because the pool tries to pull 52.78e18. On top of that, the missing max input check from M-1 and the deadline hardcoded to block.timestamp mean the caller has no slippage protection at all on this path.

Proof of Concept: Check the test_SellPoolTokensWrongAmount_AUDIT test in the TSwapPool.t.sol file:
Here’s the full code 
    // the M-2: sellPoolTokens passes the amount to sell as the exact WETH output, so the
    // caller pays a completely different amount of pool tokens than they asked to sell
    function test_SellPoolTokensWrongAmount_AUDIT() public {
        vm.startPrank(liquidityProvider);
        weth.approve(address(pool), 100e18);
        poolToken.approve(address(pool), 100e18);
        pool.deposit(100e18, 100e18, 100e18, uint64(block.timestamp));
        vm.stopPrank();

        uint256 amountToSell = 5e18;

        // an honest seller holding more than 5 pool tokens cannot sell them either
        vm.startPrank(user);
        poolToken.approve(address(pool), type(uint256).max);
        vm.expectRevert();
        pool.sellPoolTokens(amountToSell);
        vm.stopPrank();

        // with a lot more tokens funded, the real behaviour shows up
        poolToken.mint(user, 200e18);
        vm.startPrank(user);
        uint256 poolTokensBefore = poolToken.balanceOf(user);
        uint256 wethBefore = weth.balanceOf(user);
        pool.sellPoolTokens(amountToSell);
        uint256 poolTokensSpent = poolTokensBefore - poolToken.balanceOf(user);
        uint256 wethReceived = weth.balanceOf(user) - wethBefore;
        vm.stopPrank();

        console.log("asked to sell:", amountToSell);
        console.log("pool tokens actually spent:", poolTokensSpent);
        console.log("weth actually received:", wethReceived);

        // the caller receives exactly the number they passed in, and pays a different amount
        assertEq(wethReceived, amountToSell);
        assertGt(poolTokensSpent, amountToSell);
    }

-    function sellPoolTokens(uint256 poolTokenAmount) external returns (uint256 wethAmount) {
-        return
-            swapExactOutput(
-                i_poolToken,
-                i_wethToken,
-                poolTokenAmount,

+    function sellPoolTokens(
+        uint256 poolTokenAmount,
+        uint256 minWethToReceive,

+            i_poolToken,
+            poolTokenAmount,
+            i_wethToken,
+            minWethToReceive,
+            deadline
+        );
+    }

  1. Taking a real deadline also fixes the hardcoded uint64(block.timestamp) in the current version, which makes the deadline check on this path meaningless.

  2. swapExactInput currently returns a hardcoded 0, because its named return is never assigned. That is logged as a separate Informational finding, and it has to be fixed before this return value can be trusted.

Low

[L-1] Missing deadline check in TSwapPool::deposit, an expired transaction can still be executed

Description: deposit takes a deadline and the natspec even documents it, but the revertIfDeadlinePassed modifier is never applied, so the parameter is not read at all:

function deposit(
    uint256 wethToDeposit,
    uint256 minimumLiquidityTokensToMint,
    uint256 maximumPoolTokensToDeposit,
    uint64 deadline
)
    external
    revertIfZero(wethToDeposit)
    returns (uint256 liquidityTokensToMint)

That modifier already exists in the contract, and withdraw, swapExactInput and swapExactOutput all use it.

Impact: A deposit transaction can sit in the mempool and be included at any later time, whatever deadline the user set, and the user has no way to invalidate it. On a normal deposit the pricing damage is bounded, because minimumLiquidityTokensToMint and maximumPoolTokensToDeposit are both checked there, which is why this is Low and not higher. Note that the first deposit does not check the minimum at all, which is logged as I-6. What is missing either way is the deadline the user asked for.

Proof of Concept: Check the test_DepositIgnoresDeadline_AUDIT test in the TSwapPool.t.sol file:
Here’s the full code 
    // the L-1: deposit takes a deadline but never checks it, so an expired deadline is accepted
    function test_DepositIgnoresDeadline_AUDIT() public {
        vm.startPrank(liquidityProvider);
        weth.approve(address(pool), 100e18);
        poolToken.approve(address(pool), 100e18);

        // a deadline that has already passed
        uint64 expiredDeadline = uint64(block.timestamp - 1);

        // deposit does not look at the deadline, so it goes through
        pool.deposit(100e18, 100e18, 100e18, expiredDeadline);
        console.log(
            "lp tokens minted with an expired deadline:",
            pool.balanceOf(liquidityProvider)
        );
        assertEq(pool.balanceOf(liquidityProvider), 100e18);

        // the same expired deadline is rejected by withdraw
        vm.expectRevert(
            abi.encodeWithSelector(
                TSwapPool.TSwapPool__DeadlineHasPassed.selector,
                expiredDeadline
            )
        );
        pool.withdraw(100e18, 100e18, 100e18, expiredDeadline);
        vm.stopPrank();
    }

You can run it via

forge test --mt test_DepositIgnoresDeadline_AUDIT -vv

and you will see something like this:

Logs:
  lp tokens minted with an expired deadline: 100000000000000000000

An expired deadline is accepted by deposit and rejected by withdraw, in the same run.

Recommended Mitigation: 1. Apply the modifier that already exists in the contract:

     function deposit(
         uint256 wethToDeposit,
         uint256 minimumLiquidityTokensToMint,
         uint256 maximumPoolTokensToDeposit,
         uint64 deadline
     )
         external
+        revertIfDeadlinePassed(deadline)
         revertIfZero(wethToDeposit)
         returns (uint256 liquidityTokensToMint)
  1. The PoC has to be flipped after the fix: it currently asserts that the expired deposit succeeds, and it should expect TSwapPool__DeadlineHasPassed instead.

Informational

[I-1] 0.8.20 is compiled for Shanghai in TSwapPool and PoolFactory, PUSH0 can break deployment on some chains

Description: Both contracts are pinned to 0.8.20, and that version defaults to the Shanghai EVM version, so the compiler emits PUSH0 opcodes. Any chain that does not support PUSH0 will fail to deploy the bytecode, and Slither’s pragma detector also reports that the repo mixes pragma ranges across the imported interfaces.

Recommended Mitigation: 1. Pin the EVM version for the build if any target chain lacks PUSH0, instead of relying on the compiler default:

 [profile.default]
 src = "src"
 out = "out"
+evm_version = "paris"
  1. If PUSH0 is acceptable on every target chain, this can be closed as acknowledged, but it is worth writing down which chains were checked.

[I-2] Magic numbers and large literals in TSwapPool, the fee values should be named constants and MINIMUM_WETH_LIQUIDITY written as 1e9

Description: The fee pair and the minimum liquidity are written as bare literals. MINIMUM_WETH_LIQUIDITY = 1_000_000_000 should be 1e9, and the pricing functions use 997, 1000 and 1e18 inline. Aderyn reports both large-numeric-literal and literal-instead-of-constant for these lines, and the mistake in H-1 came from exactly this kind of hand written number.

Recommended Mitigation: 1. Use scientific notation for the large literal:

-    uint256 private constant MINIMUM_WETH_LIQUIDITY = 1_000_000_000;
+    uint256 private constant MINIMUM_WETH_LIQUIDITY = 1e9;
  1. Name the fee pair once, so both pricing functions read from the same definition:
+    uint256 private constant FEE_MULTIPLIER = 997;
+    uint256 private constant FEE_BASE = 1000;
+    uint256 private constant ONE_E18 = 1e18;
...
